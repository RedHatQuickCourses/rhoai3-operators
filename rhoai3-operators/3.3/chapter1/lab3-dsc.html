Lab 3 — Activating the AI factory (DataScienceCluster)

Operators provide potential. The DataScienceCluster provides intent.

The meta-operator is idle until you declare which RHOAI subsystems are Managed. This is how you keep idle controllers from nibbling RAM in multi-tenant clusters.

1. Strategy — selective activation

For the GenAI / MaaS-forward factory path in this journey:

  • Dashboard — Managed (Model Catalog UX).

  • Model registry — Managed with a dedicated registries namespace.

  • KServe — Managed with serving Managed (pattern shown below aligns with modern serving stack docs—validate field names against 3.3 docs if your CRD differs).

Explicitly remove components you do not need (examples below: legacy ModelMesh, Codebases, Ray) to reduce reconciliation and attack surface.

DataScienceCluster schema changes between releases. If apply fails with unknown fields, run oc explain datasciencecluster.spec on your cluster and reconcile this manifest with the installed CRD.

2. Apply the blueprint

cat <<EOF | oc apply -f -
apiVersion: datasciencecluster.opendatahub.io/v1
kind: DataScienceCluster
metadata:
  name: default-dsc
spec:
  components:
    dashboard:
      managementState: Managed
    modelregistry:
      managementState: Managed
      registriesNamespace: rhoai-model-registries
    kserve:
      managementState: Managed
      serving:
        managementState: Managed
        name: knative-serving
    modelmeshserving:
      managementState: Removed
    codebases:
      managementState: Removed
    ray:
      managementState: Removed
EOF

3. Verification

DSC phase

oc get datasciencecluster default-dsc -o jsonpath='{.status.phase}{"\n"}'

Target: Ready (may take several minutes).

Dashboard route

RHOAI 3.x commonly exposes the experience via a gateway-style route name. Fetch routes:

oc get route -n redhat-ods-applications | grep data-science-gateway

Open the URL in a browser and confirm Model Catalog and Model Registry navigation exist.
