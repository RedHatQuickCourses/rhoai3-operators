Operator architecture & data flow

Before you operate the machinery, know which room is air traffic control and which room is the runway.

Split plane mental model

Plane Responsibility

Control plane (cluster services)

OLM, operator pods, CRD controllers, cert-manager, gateway/policy operators. They reconcile desired state you declare in YAML.

Execution plane (tenant / AI workloads)

Serving runtime pods, model artifacts, GPU-bound inference, data pipelines. They burn GPU and RAM and determine TTFT/SLOs.

Your job in Phase 0 is to make the control plane boring: healthy CSVs, clean DSC phase, predictable routes—so the execution plane can be tuned for throughput instead of firefighting.

1. Operator Lifecycle Manager (OLM)

You do not “kubectl apply once and hope.” Operators are long-lived reconcilers. OLM:

  • Resolves Subscriptions to ClusterServiceVersions (CSVs) on a channel (for example stable-3.x for RHOAI).

  • Owns upgrade graphs and dependency hints when products are packaged to cooperate.

  • Surfaces failure loudly when an install plan cannot be satisfied—treat a stuck CSV as a P1 for the factory schedule.

2. Meta-operator pattern (OpenShift AI)

Installing the Red Hat OpenShift AI operator does not instantly materialize every UI and serving pod. The operator is a factory manager waiting for a DataScienceCluster CR.

Typical namespace split (exact names can vary slightly by version—verify in docs):

  • redhat-ods-operator — operator subscription and controller for the meta-operator.

  • redhat-ods-applications — dashboard and many user-facing control components.

  • rhoai-model-registries — model registry footprint when enabled (your governed title office for model artifacts).

Architectural decision: Keep registry and serving concerns logically separate even when the same team operates them. Registry downtime should not imply serving meltdown, and vice versa—design network policy and upgrades accordingly.

3. Lifecycle — happy path data flow

The following is the order of operations your cluster should follow:

OperatorHub / CatalogSource
        → Subscription (channel)
        → InstallPlan approval (if manual)
        → CSV Succeeded
        → Operand CRs (e.g., NodeFeatureDiscovery, DataScienceCluster)
        → Managed workloads (dashboard routes, registry, serving controllers)
        → Data scientist / SRE workloads (InferenceService, llm-d, MaaS gateways)

Traffic cop analogy: OLM is the DMV issuing licenses; the DSC is the zoning board that says which buildings may open on the lot; gateways and policies are the municipal traffic lights before cars reach the highway on-ramp (your GPU nodes).

4. Mapping operators to architectural lanes

Lane A — Physical truth (accelerators)

  • NFD labels nodes with hardware capabilities.

  • GPU operators attach drivers and device plugins so Kubernetes can schedule resources.limits on GPUs.

  • Kueue arbitrates who waits when demand exceeds supply.

Lane B — Secure serving

  • cert-manager backs TLS needs for serving stacks that expect in-cluster issuers.

  • KServe / Knative stacks (when enabled via DSC) provide the serving substrate referenced throughout the journey.

Lane C — Scale-out and MaaS-style exposure

  • Leader Worker Set enables distributed pod topologies.

  • Connectivity Link brings the policy/gateway story for governed externalization of models—pair with your org’s API management standards.
